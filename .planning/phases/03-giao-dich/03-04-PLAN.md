`TransactionBulkService` gọi `transactionWriter.write(cmd)` mà bản thân method gọi trong
`TransactionBulkService` KHÔNG có `@Transactional` bao ngoài, thì lời gọi `write()` tự mở transaction

một DB transaction riêng" mà KHÔNG cần thêm `propagation = REQUIRES_NEW` tường minh, miễn
`TransactionBulkService.processBatch()` (method vòng lặp) KHÔNG tự đặt `@Transactional` ở ngoài vòng
lặp. Đây là điểm dễ nhầm nhất — PHẢI viết method điều phối vòng lặp (`processBatch`) là method
THƯỜNG (không `@Transactional`), để mỗi lần gọi `transactionWriter.write(cmd)` bên trong vòng lặp là
một lời gọi cross-bean độc lập, đi qua Spring AOP proxy thật, mở transaction riêng cho từng dòng.

`IdempotencyAspect.around()` (đã tồn tại từ Phase 1, KHÔNG sửa) — bọc NGOÀI method controller đánh
dấu `@Idempotent`:
```java
@Around("@annotation(com.datn.financeapp.common.idempotency.Idempotent)")
public Object around(ProceedingJoinPoint pjp) throws Throwable {
    ...
    // Insert processing -> pjp.proceed() (toàn bộ nghiệp vụ bulk chạy ở đây) -> markCompleted
    // Nếu pjp.proceed() ném exception -> xoá bản ghi processing, throw lại nguyên vẹn
}
```
Vì `@Idempotent` gắn trên method Controller (không phải Service), và Controller gọi
`transactionBulkService.processBatch(...)` — method đó KHÔNG mang `@Transactional`, nên
`IdempotencyAspect` KHÔNG mở transaction bao trùm cả lô. Mỗi dòng bên trong `processBatch` vẫn tự mở
transaction riêng qua `TransactionWriter.write()`. Đây chính là cách giải quyết D-35a.
